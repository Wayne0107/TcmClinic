# 規格索引（Specs Index）

本檔為所有功能規格的**總覽索引**：資料夾結構、各規格狀態、依賴關係、**相關規格反查**與**延後事項**。

規格採 **UDS 規格驅動開發（SDD）格式**（依據 [`.standards/spec-driven-development.ai.yaml`](../.standards/spec-driven-development.ai.yaml)）：
每個功能一份 `spec.md`，編號 `SPEC-NNN` 寫在標頭；需求、驗收條件、技術設計、測試計畫與實作紀錄都在同一份檔案內。

> 📌 **維護原則**：規格內容有變動（空殼填入正式規格、狀態推進、新增規格）時，同步更新本檔——
> ①「功能規格一覽」該列的狀態與「相關規格」；②「功能領域對照」歸入對應領域。
> 若某規格**修改／取代**了舊規格，於雙方「相關規格」欄互相註明。

> 📦 **範本內建規格**：下列 ✅ 規格隨範本沿用自源專案（CHB），已實作於骨架。規格內文提到的分行、企業、開狀申請、系統參數、CHB 選單／角色等屬源專案業務，範本已移除；以骨架程式碼與測試為準。

## 資料夾結構

```
specs/
├── README.md
├── 管理業務/
│   └── 系統管理作業/（3）
└── 其他/（9＋架構決策，跨選單的基礎／橫切規格）
    └── 架構決策/（跨選單的 ADR）
```

| 規則 | 說明 |
|------|------|
| 選單分層 | `specs/<業務>/<作業>/<功能>/`，資料夾名＝選單顯示名稱（繁體中文），一個選單葉節點＝一份規格 |
| 跨選單 | 不對應單一選單的底層能力（授權模型、稽核、基礎設施等）放 `specs/其他/` |
| 不加編號 | 資料夾不加數字前綴；選單順序以本索引為準（檔案總管依字元排序，不等於選單順序） |
| 名稱中的 `/` | 資料夾名稱不能含 `/`，改用 `、`（如「繕製/上傳單據」→ `繕製、上傳單據`） |
| 選單資料源 | 後端選單種子 `MenuSeedData.cs`（`backend/src/TcmClinic.Api.Infrastructure/Data/`） |

> 選單樹以**後端種子為權威來源**，前端由 `GET /me/menus` 取得。範本種子只有「管理業務 › 系統管理作業」（角色權限維護、帳號維護、個人資料維護）與後台選單管理 `/admin/menus`；新增功能時，其選單隨規格加入種子的選單樹（已實作者並加入初始授權）。

> 💡 `git status` 若將中文路徑顯示為 `\351\200\262...`，執行 `git config core.quotepath false` 即可正常顯示。

### SPEC-ID 編號

SPEC-002～SPEC-065 為範本內建規格的編號（沿用源專案，程式碼註解、測試標記 `// @SPEC-NNN @AC-N` 都以此引用，**不得重新編號**）；中間跳號屬源專案已移除的業務規格。**新規格從 SPEC-066 起接續**，取下一個未用的編號；帳號維護空殼沿用 SPEC-058。

程式碼註解以「SPEC-004」「設計決策 R3」「SPEC-004 API 契約 §3」等形式引用規格內的編號；規格內的 FR／R／§ 編號保留原樣，不重排。

## 延後事項（Deferred）

規格內記錄的延後項目，其可追蹤出口在此（UDS [deferred-item-exit](../.standards/deferred-item-exit.ai.yaml)：延後項目必須離開規格文件，且出口編號緊鄰該項目）。完成或決定放棄時，更新此表與規格內對應項目。

**登記範圍**：只登記「明確延後、之後要做」或「待決策」的項目。規格中單純劃定範圍的語句（如「IP 層級節流不在本次範圍」）與 Assumptions 不必登記。

## 如何維護

完整的情境流程（新功能、修 bug、修改既有規格、重構）見 [docs/WORKFLOW.html](../docs/WORKFLOW.html)。

### 撰寫規格（新功能或填入空殼）

1. 需求模糊時先以 `/universal-dev-standards:brainstorm`、`/universal-dev-standards:requirement` 釐清
2. 釐清前先查其他規格是否已對同一議題拍板（Clarifications 段）與 `.project-context/` 的專案決策
3. 依序執行 `/universal-dev-standards:sdd discuss`、`create`、`review`、`approve`，在該功能的 `spec.md` 撰寫（空殼沿用標頭的 SPEC-ID）
4. 核准後執行 `/universal-dev-standards:derive-bdd` 產出 `.feature`，再 `sdd implement`、`sdd verify`；PR 以 squash 合併後 `sdd archive`
5. 標頭狀態依序推進：Draft → Review → Approved → Implemented → Archived（合併歸檔後改為 Archived）
6. 更新本檔該列的「狀態」與「相關規格」，並歸入「功能領域對照」；有 ADR 時補進上方 ADR 索引

### 新增規格

- **選單新增葉節點**：放進對應的 `<業務>/<作業>/` 資料夾（新作業就新建資料夾），取下一個未用的 SPEC-ID，選單一併加入 `MenuSeedData.cs`，並補進本檔對應表格
- **跨選單的基礎／橫切規格**：放 `specs/其他/<中文名稱>/`
- 若修改了某舊規格：舊規格標頭與本檔該列註明「⚠️ 部分被 SPEC-NNN 修改」；新規格以 UDS delta 段落（ADDED／MODIFIED／REMOVED Requirements）註明「改 SPEC-NNN FR-YYY」
- 選單改名或搬移時，同步搬移資料夾並更新本檔連結

### 規格格式要點

- 每條 AC 必須有驗證項（測試方法或明確的手動步驟），否則降級為設計意圖（UDS 規則 SDD-AC-VERIFIED）
- 驗證項列出的測試方法，須在測試程式碼屬性上方加 `// @SPEC-NNN @AC-N` 標記（見 [docs/TESTING.md](../docs/TESTING.md) §5），兩邊保持一致
- 實作完成後在「實作紀錄（Archive）」記下主要提交；commit 訊息以 `Refs: SPEC-NNN` 引用規格
- 規格內有延後或未完成項目時，在上方「延後事項」表登記 DEF 編號並寫回規格
- 範例：[開發模式可見全部選單](./其他/開發模式可見全部選單/spec.md)

> 💡 提示：`spec.md` 記錄「要做什麼、為何這樣決定」；本索引記錄「有哪些規格、彼此關係」；
> **程式碼與測試才是「現況行為」的最終真相**。三者分工，避免任何單一文件試圖記錄全部。
