# ADR-002 跨表關聯一律以 ID 外鍵參照，不用業務代碼

> 📦 本 ADR 隨範本沿用自源專案（CHB），決策本身仍適用於範本。背景、影響與相關連結中提到的舊系統、分行、企業、開狀申請、系統參數等屬源專案業務，相關規格、資料表與 migration 範本已移除；以骨架程式碼與測試為準。

## 背景（Context）

舊系統 eISsuei 以業務代碼串接資料表，例如使用者、單據以 7 碼機構代碼字串指向分行，企業隸屬分行以「機構代碼＋統編」當複合主鍵。新系統初期沿用這種做法（`SysUser.BankId`、`LcApplication.ApplicantBankId`），導致：業務代碼若變更或重用，關聯就斷；資料庫無法以外鍵保證參照完整性；同一個「分行」在不同表以不同格式出現。

## 考慮過的選項

1. **一律以被參照表的 `Id` 主鍵當外鍵**，業務代碼只作顯示與查詢條件。
2. **沿用業務代碼字串**（邏輯關聯，不建外鍵）：與舊系統一致、轉換資料簡單。
3. **外鍵指向業務欄位**（EF `HasPrincipalKey` 指向 alternate key）：有外鍵約束，但仍綁在可變的業務代碼上。

## 決策結果

採用 **選項 1**，適用所有資料表（業務表、系統表、append-only 稽核與日誌表）：

- 外鍵欄位命名 `<被參照實體>Id`，型別用被參照聚合的 Vogen 強型別 ID，`OnDelete` 必須明確宣告。
- 外部輸入（API、匯入檔）以業務代碼識別對象時，應用層先解析為 `Id` 再寫入。
- 需保留「當下的值」時另存快照欄位，只供顯示。
- 被參照對象還沒有主檔時，先建主檔再以 `Id` 參照（例：企業主檔建立前，開狀申請的申請企業統編為過渡快照，見 DEF-010）。
- **唯一例外**：標準欄位 `CreateUser`／`ModifyUser` 存登入帳號（操作者紀錄，不是關聯）。

**理由**：參照完整性由資料庫保證；業務代碼可以改、可以重用而不影響關聯；與 Vogen 強型別 ID（ADR-005）一致。

## 後果

- **好**：關聯不會因代碼變更而斷；刪除行為在資料庫層強制（例：分行有企業隸屬時不能刪）；查詢一律以 ID join。
- **壞**：API 常以業務代碼對外（如 4 碼分行代碼），每次寫入都要多一次「代碼 → ID」解析；舊資料轉移時需要對照表；已上線的字串欄位要逐一改造（各規格自行處理）。
