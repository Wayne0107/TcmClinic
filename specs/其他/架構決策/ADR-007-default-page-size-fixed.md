## 背景（Context）

舊系統（eISsuei）的清單每頁筆數取自系統參數「查詢列表分頁筆數」（初始 10）。SPEC-016 系統參數維護（2026-10-02）照搬這個做法：所有分頁清單沒有指定 `pageSize` 時，都讀這個參數。

但前端（TcmClinic.Web，另一團隊維護）每個清單頁面都已自行設定每頁筆數，查詢時都會帶 `pageSize`。SPEC-016 R14 預先提醒過：前端固定帶 `pageSize`，系統參數就不會生效。所以這個參數實際上沒有作用，留在畫面上只會讓管理者以為改了有用。

2026-10-06 使用者決定「系統參數維護」不再提供分頁設定，這個參數要移除。清單沒指定 `pageSize` 時（例如直接呼叫 API），仍需要一個預設筆數。

現有 5 個分頁清單受影響：分行（SPEC-014）、角色維護（SPEC-012）、待受理開狀申請（SPEC-011）、使用者（SPEC-004）、企業（SPEC-059）。

## 考慮過的選項

1. **固定 10 筆**：等於原參數的初始值，5 個清單的實際行為不變。
2. **固定 20 筆**：回到 SPEC-016 之前部分清單的預設值；分行、角色、企業清單會從 10 變成 20。
3. **`pageSize` 改為必填**：前端不帶就回 400。前端目前雖然每頁都帶，但這會改變既有 API 契約，直接呼叫 API 或日後新頁面漏帶時就會失敗。

## 決策結果

採用 **選項 1**：

- 未指定 `pageSize`、或指定 0 或負數時，每頁 **10** 筆；指定正整數時依指定值，上限 100。
- 請求的 `pageSize` 維持可空（`int?`），不在 request DTO 設初始值。FastEndpoints 只繫結請求中出現的查詢參數，DTO 初始值會在進入 handler 前生效，handler 就分不出前端有沒有指定。
- 規則集中在 UseCases 的 `PageSizeResolver`（`backend/src/TcmClinic.Api.UseCases/Paging/`）。它是不讀資料庫的純函式，各清單 handler 都呼叫它，不各自寫死。
- 回應的 `pageSize` 與 `Link` 標頭一律用實際採用的筆數。

**理由**：

- 實際行為和移除前參數為初始值時完全相同，前端與既有測試的預期都不用改。
- 規則仍集中在一處，日後要調整只改一個常數。
- 清單查詢不再多一次讀參數的資料庫查詢。

## 後果

- **好**：
  - 清單預設行為穩定，不會因為有人改參數而全系統一起變。
  - 前端不再需要遵守「沒選就不要帶 `pageSize`」的串接約定（原 SPEC-016 R14）。
- **壞**：
  - 管理者不能再從畫面調整預設筆數，要改就得改程式並重新部署。由於前端各頁面已自行決定每頁筆數，這個預設值只影響沒帶 `pageSize` 的呼叫，實際影響很小。
  - 與舊系統的行為不同，資料移轉時舊系統 `PARAMETER_ID = 1` 不移轉。
