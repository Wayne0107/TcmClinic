# ADR-004 多人共用維護的資料以 RowVersion 樂觀併發，雙道防線回 409

## 背景（Context）

舊系統修改資料採「後寫覆蓋」，兩位使用者同時修改同一筆時，先送出者的修改會被無聲覆蓋；整份替換的清單（角色可見選單、轄下分行、隸屬分行）更會把別人新增的項目一起蓋掉。受理開狀申請也需要防止同一張申請被重複處理。

## 考慮過的選項

1. **RowVersion 樂觀併發，版本權杖必填**：讀取時回傳 `rowVersion`，修改時原樣回帶，不符回 409。
2. **RowVersion 選填**：前端有帶才檢查。
3. **資料庫層悲觀鎖**。
4. **後寫覆蓋（不控制）**：只適合只有本人會改的資料。

## 決策結果

多人共用維護的資料採用 **選項 1**：

- 聚合根加 `RowVersion`（SQL Server `rowversion`）；明細查詢回傳 Base64 `rowVersion`；修改請求**必填**，缺漏回 400、不符回 409。
- **第一道防線**：用例層比對客戶端版本與載入的版本，不符回 `Result.Conflict` 並記失敗操作紀錄。
- **第二道防線**：儲存時的極短競態窗由 EF 擲 `DbUpdateConcurrencyException`；用例重查版本判定，未攔下者由 `Program.cs` 的全域中介層轉為 409。
- 只改子集合（清單整份替換）時也要「觸碰」聚合根，使版本前進。
- 刪除不做版本檢查（刪除已有伺服器端保護且為軟刪除）。
- 只有本人會改的資料（如個人資料）可採後寫覆蓋，須在規格中說明。

**理由**：後端獨立保證「並行不靜默覆蓋」，不依賴前端是否配合；與 SPEC-011 既有做法一致（憲章原則 V）；不需要資料庫鎖。

## 後果

- **好**：同時修改時後送者明確收到「資料已被他人變更，請重新載入」；整份替換的清單不會互相覆蓋。
- **壞**：前端必須保存並回帶 `rowVersion`；使用者遇到衝突要重新載入再改；每個修改端點都要寫兩道防線的處理與測試。
