## 背景（Context）

系統原本以「超級管理員」特例與防鎖死邏輯管理權限，選單可見性只決定「看得到哪些頁面」，API 本身沒有對應的授權。使用者要求「設定哪些角色可以讀取、操作哪些資料」，而 TcmClinic.Web 的每個頁面與後端 API 幾乎是一對一。需要一套讓「角色能看到哪個選單」直接決定「能呼叫哪些 API」的授權方式。

## 考慮過的選項

1. **以選單路由（`Route`）作為授權鍵**：端點宣告守門選單，使用者的可見選單集合含該選單就放行（讀寫一致）。
2. **在選單加獨立的 `PermissionKey` 欄位**：選單改名時權限鍵不變，但要擴張資料結構。
3. **後端路由前綴約定對應**（如 `/users` 對應 `/admin/users`）：不需宣告，但脆弱，難涵蓋巢狀路由。
4. **每次請求即時查資料庫判斷**：不必 claims 化，但每個端點多一次查詢。

## 決策結果

採用 **選項 1**，且**讀取與寫入都依可見性授權**（對稱模型）：

- 登入驗證時把使用者可見的選單路由寫成 `menu` claims；端點以 `Policies("MenuAccess:<選單 value>")` 宣告守門選單。
- 跨頁共用的查詢可宣告多個選單（`MenuAccess:A|B`，任一命中即可）。
- 只需登入、不受選單控管的端點屬例外，須在規格中明文記錄（例：SPEC-014 `GET /branches/options`）。

**理由**：零資料表變更，直接沿用既有的「角色 ↔ 可見選單」；可見性成為單一授權來源；動態原則供應器讓新頁面不必逐一註冊原則。

## 後果

- **好**：權限設定只有一個地方（角色權限維護頁）；每個新功能只要宣告守門選單即受控；授權矩陣可用測試護欄偵測回歸。
- **壞**：選單的 value 是授權鍵，**不可任意改名**，改名會讓端點宣告與可見性對不上；跨頁共用查詢需要個別判斷是否開例外。
