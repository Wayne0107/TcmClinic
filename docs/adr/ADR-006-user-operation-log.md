# ADR-006 使用者操作紀錄 SysUserLog：獨立交易、盡力寫入、成功失敗都記

## 背景（Context）

舊系統每個維護功能都寫 `USER_LOG`（功能、動作、成功或失敗、內容），「使用者存取記錄」選單以此查詢。新系統已有兩種紀錄，但都不適合：資料表異動紀錄（SPEC-006）只在資料成功寫入時產生，記不到失敗；資料訪問日誌（SPEC-010）的語意是敏感資料讀取。需要一個能記「每次操作、不論成敗」的紀錄。

## 考慮過的選項

1. **新增 append-only 表 `SysUserLog`，以獨立 DbContext 寫入，盡力寫入、失敗不拋**。
2. **只寫應用程式日誌（Serilog）**：系統內無法查詢，「使用者存取記錄」沒有資料來源。
3. **擴充 `SysAccessLog` 加修改類型**：違反其「讀取旁路」定義。
4. **與主交易共用同一個 DbContext**：主交易失敗後追蹤器殘留的髒資料會被一起送出。

## 決策結果

採用 **選項 1**：

- Core 定義 `IUserLogRecorder`；Infrastructure 以 `IServiceScopeFactory` 建立獨立 `AppDbContext` 寫入，主交易失敗或回滾都不影響紀錄落庫；寫入失敗只記告警、不拋例外。
- 欄位：功能代碼（採新系統選單語意，如 `BranchData`、`CorporateData`）、動作（`Add`／`Modify`／`Delete`…）、結果（`Success`／`Failure`）、內容訊息；操作者與時間由標準五欄記錄（ADR-003）。
- **記錄範圍**：通過請求格式驗證、進入用例的每一次操作，成功、業務規則失敗、並行衝突、非預期錯誤都記；格式驗證失敗與查無資料不記。
- **內容不得含密碼或例外原文**；非預期錯誤只記固定訊息（如「企業資料維護 [xxxx]新增失敗」）。

**理由**：失敗紀錄不會被主交易回滾吞掉；與舊系統 `USER_LOG` 對齊，提供「使用者存取記錄」查詢來源；不污染既有兩種紀錄的語意。

## 後果

- **好**：每個維護功能的操作都可追溯；新功能只要注入 `IUserLogRecorder` 即可沿用。
- **壞**：每次操作多一次獨立寫入；盡力寫入代表極端情況下可能漏記（以告警日誌補償）；各功能要自行維護一致的功能代碼與訊息格式。
