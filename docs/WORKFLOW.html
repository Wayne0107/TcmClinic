先看這裡：共通規則

停止點 我會停下來等你回覆 AI 執行 我自動做完 選用 可略過 Git commit／push／PR
項目規則
指令名稱一律打全名 /universal-dev-standards:xxx。這個環境不認短名 /sdd。
分支規格工作 feature/NNN-短名（小寫英文，例：feature/058-account-maintenance）；修 bug fix/NNN-短名；非規格工作 feature/<短名>。
commit每個階段做完、建置與測試全綠後我直接 commit 並回報訊息（2026-10-06 起）。每個 commit 都必須建置成功、測試全綠。
commit 格式繁中類型：新增 修正 文件 測試 重構 維護 效能 樣式 建置 整合 回退 安全。例：新增(058): 帳號維護端點，實作類加頁腳 Refs: SPEC-058。
TDD 紅燈紅燈只在本機跑、不提交；把「哪個測試、為什麼失敗、日期」記在規格的「實作紀錄」。
合併分支 push 到 GitHub 開 PR → code-review → checkin → squash 合併。合併後刪除分支。沒有 BLOCKING 時我自動完成整個流程，不再先問（2026-10-08 起）。
測試執行dotnet run --project backend/tests/<測試專案>（dotnet test 會失敗）；整合、功能、驗收測試需要 Docker，依序執行。

① 新功能 → 新規格

新增一個功能（通常對應一個選單）。規格寫在 specs/<業務>/<作業>/<功能>/spec.md；已有空殼（如範本內建的帳號維護）就沿用標頭的 SPEC-ID。

專案約定「不擅自新增規格沒有要求的功能」。UDS 檢查清單建議的額外功能（MFA 等）我會先列為待決事項，由你決定要做才納入規格。
  1. 發想與釐清需求 選用 停止點
    /universal-dev-standards:brainstorm <功能構想>
/universal-dev-standards:requirement

    需求還模糊時先發想，再依 INVEST 原則寫使用者故事與驗收條件；需求已明確可略過。

    你回覆：確認需求，或補充要釐清的地方。

  2. 決定規格位置

    有選單的功能放進對應的 specs/<業務>/<作業>/<功能>/（新選單要一起加進選單種子 MenuSeedData.cs）；跨選單的基礎能力放 specs/其他/<名稱>/。SPEC-ID 取下一個未用的編號（見 specs/README.md）。

  3. 討論灰色地帶 停止點
    /universal-dev-standards:sdd discuss

    我會先查其他規格的 Clarifications 與 .project-context/ 是否已拍板，再用選單一次問 3～4 題；標「(建議)」的是我推薦的選項。

    你回覆：選擇答案，看完 Discuss Summary 後回「確認」。

  4. 撰寫規格 AI 執行 停止點
    /universal-dev-standards:sdd create

    寫進 specs/<業務>/<作業>/<功能>/spec.md；重要決策另寫 docs/adr/ADR-NNN-短描述.md；同步更新 specs/README.md（狀態、DEF）與 docs/adr/README.md（ADR 索引）。

    你回覆：確認（或要改的地方）。之後我提示 commit：文件(NNN): 撰寫<功能>規格。

  5. 審查規格 停止點
    /universal-dev-standards:sdd review

    逐項檢查需求、驗收條件、技術設計、測試計畫；列出建議修改。看規格時有疑問直接問（例：「資料表欄位有哪些？」）。

    你回覆：「好，現在改」或「直接進 approve」。

  6. 核准 停止點
    /universal-dev-standards:sdd approve

    你回覆：「核准」。規格狀態改 Approved。

  7. 推演 BDD 情境 AI 執行 停止點
    /universal-dev-standards:derive-bdd

    把驗收條件轉成驗收測試專案的 .feature：backend/tests/TcmClinic.Api.AcceptanceTests/<選單路徑>/<選單名>.feature（選單路徑與 specs/ 相同，一個選單一個資料夾），每個 Scenario 標 @SPEC-NNN @AC-N。查詢次數、契約快照這類不適合 Gherkin 的驗收條件，照舊用功能或整合測試。Reqnroll 已在範本中引進。

    你回覆：確認寫入。

  8. 實作（TDD） AI 執行 停止點 Git
    /universal-dev-standards:sdd implement

    先開分支 feature/NNN-短名、跑四層測試（單元、整合、功能、驗收）當基線，產出實作計畫。之後依層實作：領域模型 → 資料庫與種子 → 用例 → 端點／BDD 步驟。每層先在本機跑紅燈並記到實作紀錄，再實作到全綠，然後提示 commit。

    你回覆：「確認 A」（每階段停）或「確認 B」（一路做完）；每次提示 commit 時回「好」。

  9. 驗證 AI 執行 停止點
    /universal-dev-standards:sdd verify

    重跑四層測試，逐條驗收條件列出程式碼與測試位置，產出驗證報告；通過後狀態改 Implemented。

  10. 需求追溯檢查 選用
    /universal-dev-standards:ac-coverage

    比對規格驗收表與測試標記，確認每條驗收條件都有測試。

  11. 程式碼審查與提交前檢查 停止點
    /universal-dev-standards:code-review
/universal-dev-standards:checkin

    有問題就先修，修完再跑一次。

  12. push、開 PR、squash 合併 Git 
    push 並開 PR

    我自動 push 並開 PR（/universal-dev-standards:pr），審查沒有 BLOCKING 就合併並刪除分支。PR 合併採 squash，合併訊息例：新增(058): 帳號維護 (#12)。

  13. 歸檔 AI 執行
    /universal-dev-standards:sdd archive

    實作紀錄補上合併 commit 與 PR 編號，規格狀態改 Archived，specs/README.md 該列改 ✅。

② 修 bug

  1. 開分支 Git

    fix/NNN-短名（NNN 是出問題的規格編號）。

  2. 寫重現問題的測試（紅燈） AI 執行
    /universal-dev-standards:tdd <問題描述，例：停用帳號後仍可登入>

    先寫一個會失敗的回歸測試，確認是因為這個 bug 而失敗；紅燈結果記在該規格的實作紀錄。

  3. 修正到全綠 AI 執行 Git

    最小修正讓測試轉綠，四層測試全過後提示 commit：修正(NNN): …。

  4. 規格要不要改？

    bug 是因為規格沒寫清楚時，在規格的 Clarifications 補一筆；行為和規格不同時照情境 ③ 處理。

  5. 審查與合併 Git 停止點
    /universal-dev-standards:code-review
/universal-dev-standards:checkin

    之後自動 push、開 PR、squash 合併並刪除分支。

③ 修改既有規格（需求變更）

  1. 討論變更 停止點
    /universal-dev-standards:sdd discuss <規格路徑> 要把……改成……
  2. 寫變更（delta） AI 執行 停止點

    在規格加 ADDED／MODIFIED／REMOVED Requirements；變更影響到其他規格時，舊規格標頭與索引註明「⚠️ 部分被 SPEC-NNN 修改」。改了原本的決策就另開新 ADR 取代舊的。

  3. 審查、核准
    /universal-dev-standards:sdd review
/universal-dev-standards:sdd approve
  4. 補 BDD 情境、實作、驗證
    /universal-dev-standards:derive-bdd
/universal-dev-standards:sdd implement
/universal-dev-standards:sdd verify

    只推演有變動的驗收條件。

  5. 審查、合併、歸檔 Git

    code-review → checkin → PR（squash）→ sdd archive。

④ 重構／技術債

  1. 評估做法 停止點
    /universal-dev-standards:refactor <要重構的範圍>

    不改行為就不寫規格；升級套件依 DEPENDENCIES.md（同次更新 THIRD-PARTY-NOTICES.md）。

  2. 小步重構，每步全綠 AI 執行 Git

    分支 feature/<短名>；每一步測試保持全綠，提示 commit：重構(模組): … 或 維護(deps): …。覆蓋率不得下降。

  3. 審查與合併 Git

    code-review → checkin → PR（squash）。

⑤ 決策與記憶要記在哪裡

情況記在哪裡誰決定存
某條規格討論出的答案該規格的 Clarificationsdiscuss 時你回答即記錄
重要的架構或設計決策（有替代方案、影響長遠）docs/adr/ADR-NNN-短描述.md；索引在 docs/adr/README.md寫規格時我提議，你核准規格即生效；決策改變時另開新 ADR 取代
全專案的約定（「之後都…」「就這樣定」）.project-context/<主題>.md（PRJ-YYYY-NNNN）我提議，你同意才存
開發經驗（踩雷、解法、工具用法）.memory/（MEM-YYYY-NNNN，依類別分檔）我提議，你同意才存
延後、待決的事項specs/README.md 延後事項表（DEF-NNN）並寫回規格規格撰寫或實作時登記

規格狀態

Draft→Review→Approved→Implemented→Archived
狀態由哪個指令改意思
Draftsdd create規格撰寫中（選單空殼也是 Draft）
Reviewsdd review審查中
Approvedsdd approve已核准，可以推演與實作
Implementedsdd verify實作完成並通過驗證
Archivedsdd archive已合併並歸檔

與原版 UDS 仍不同的地方

開發流程大多已照原版 UDS。下面幾項維持專案做法，完整清單見 AGENTS.md「已裁決的衝突」。

項目本專案原版 UDS原因
規格位置選單分層資料夾的 spec.mdspecs/SPEC-XXX.md一個選單一份規格，依選單分層好找
E2E 測試不設每條驗收條件要 E2E本專案只涵蓋後端，前端另一團隊負責
CHANGELOG不維護開發時更新 [Unreleased]進度記在 specs/README.md
docs/ 檔名大寫（TESTING.md）小寫 kebab-case避免大量引用改名
API 與資料庫慣例PascalCase、400／409、page／pageSize…snake_case、422、limit…沿用源專案已定的契約與資料表慣例
本頁由 AI 依專案規範產生，規則以憲章、AGENTS.md、docs/ 為準；規則改變時同步更新本頁。
